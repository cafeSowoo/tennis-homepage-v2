## 1. 문서 우선순위와 확정된 목표

앞으로의 개발 방향은 이 문서를 우선한다. 이전 문서는 완료 증거와 전환 전 구조를 설명하는 이력이며 삭제하지 않는다. 아래 권장 설계는 구현의 출발점이고, 미정 사항은 확정된 요구로 취급하지 않는다. 문서 작성 요청 자체는 DB 변경·데이터 이전·운영 전환·배포 요청이 아니다.

사용자가 명시한 목표:

- V2에서 회원들이 직접 일정을 만들고 수정·삭제하며 참석/불참과 댓글을 관리한다.
- 카카오 로그인은 유지하되, 카카오톡 일정 동기화에 의존하지 않는 홈페이지로 운영한다.
- 이미 만든 기능을 최대한 재사용하고 V1과 V2가 서로 간섭하지 않게 한다.
- V1과 기존 동기화는 V2 안정화까지 유지하며, 종료 여부와 시점은 이후 별도로 결정한다.

작업 경계:

- V1 폴더 `/Users/dorm/coding/tennis-homepage`, 기존 배포와 기존 DB 테이블·정책·동기화 작업을 임의로 변경하거나 삭제하지 않는다.

## 2. 출발점과 재사용 범위

2026-09-17 설계 검토에서 로컬 코드·계획서와 원격 DB 컬럼·정책·트리거를 확인했다. 아래는 당시 확인 결과이며 구현 전에 다시 확인한다.

- 현재 V1/V2는 `schedules`, `discussions` 등 운영 데이터를 공유한다. 기존 일정 출처는 Kakao 160개, 홈페이지 17개, seed 32개였다.
- Kakao 로그인, `club_member_accounts` 승인 및 `members` 연결, 본인 RSVP, 회원 댓글 작성·본인 삭제, V2 저장소 격리가 구현돼 있다.
- 기존 자동 테스트 12개와 DB rollback 테스트가 통과했다. 새 전용 테이블과 권한 구조는 아직 검증하지 않았다.
- 일정 생성·수정·삭제는 owner 이메일 기반이다. `host_id`는 있지만 작성자 전용 불변 식별자는 없다.
- 현재 일정 수정은 참석자 배열까지 함께 저장한다. 회원 편집을 열기 전에 일정 정보 수정과 RSVP 저장을 분리해야 한다.
- 현재 RSVP는 Kakao 원본·override·배열·불참 테이블을 조합한다. 독립 운영에서는 이 중복 저장 구조를 새로 만들지 않는다.
- 후속 A단계에서 실제 자동화 설정 `automation-4`가 ACTIVE이며 기존 `schedules`, `members`, `courts`, `court_units`를 대상으로 하고 댓글을 제외하는 것을 확인했다. 후속 조사에서 8월 26일 기존 일정 SQL 쓰기와 9월 14~17일 로그아웃으로 인한 변경 없음 보고를 확인했다. 현재 SQL 도구의 postgres/RLS 우회 권한도 확인했으나 과거 실행 역할과 동일함을 증명하지는 않는다.
- 기존 `court-images`, `schedule-photos`는 공개 bucket이다. 새 회원 전용 사진을 제공한다면 별도 private bucket이 필요하다. `/club/` 화면의 anon 조회와 공개 JSON fallback도 전환 범위에 포함한다.

재사용: 로그인과 세션 격리, 회원 승인 연결, 달력·상세·작성 화면, 댓글 UI, 회원 권한 확인 및 행 잠금의 검증 원칙.

변경: V2 일정/참석/댓글 데이터 접근, 작성자 권한, 일정 수정 저장 범위, 서버 입력 검증. 기존 RPC·정책을 덮어쓰지 않고 새 경로를 추가한다.

## 3. 권장 데이터 경계

**같은 Supabase 프로젝트를 사용하되, V2 일정·참석·댓글은 별도 테이블로 분리한다.** 아래 전용 테이블과 RPC를 B단계에서 추가 마이그레이션으로 구현했다. 기존 테이블은 유지한다.

| 영역 | V1 및 기존 동기화 | V2 독립 운영 |
| --- | --- | --- |
| 인증·회원 연결 | 기존 Google 관리자 유지 | 기존 Kakao Auth·승인 연결 재사용 |
| 일정 | 기존 `schedules` | 새 `v2_schedules` |
| 참석 | 기존 배열·override·불참 테이블 | 새 `v2_schedule_rsvps` |
| 댓글 | 기존 `discussions`·Kakao 원본 | 새 `v2_discussions` |
| 회원·코트 | 기존 데이터 및 관리 경로 | 우선 공통 참조, 일반회원 수정 금지 |
| 사진 | 기존 저장 경로·권한 유지 | 회원 업로드 제공 시 V2 전용 경로 또는 bucket |

기존 테이블에 `source=v2`만 추가하는 안은 V1의 조회·owner 권한·동기화 로직까지 구분값을 지켜야 하므로 채택하지 않는 것을 권한다. 별도 Supabase 프로젝트는 가장 강한 격리지만 인증·승인·사진 이전 비용이 커 현재 우선안에서 제외한다.

같은 프로젝트의 테이블 분리는 완전한 격리가 아니다. Auth 설정, 회원 활성 상태, 코트 정보, 프로젝트 장애와 높은 권한의 DB 작업은 여전히 공유된다. V2 도입을 이유로 공통 정책을 광범위하게 바꾸지 않는다. 높은 권한의 동기화 작업에는 RLS만으로 격리가 보장되지 않으므로 실제 쓰기 대상을 확인한다.

### 데이터 원칙

- 일정: UUID 등 충돌 없는 ID, 제목, 날짜·시작/종료 시각, 코트, 작성자 회원 ID, 진행자 회원 ID, 정원, 모집 상태, 취소 상태, 생성/수정 시각, 수정 버전. 작성자와 진행자는 구분한다.
- 작성자는 서버가 로그인·승인 연결로 결정하며 일반 편집으로 변경할 수 없다. 인증 계정 ID를 감사 정보로 남기는 세부 방식은 구현 설계에서 정한다.
- RSVP: `(schedule_id, member_id)`당 한 행, 참석/불참/미정 상태. 행이 없는 회원도 미응답으로 표시할 수 있게 의미를 정한다. 참석자 배열을 별도 원본으로 중복 관리하지 않는다.
- 정원은 기본 16명으로 하고 일정 편집 권한자가 일정별로 변경할 수 있다(사용자 확정). 기존 16명 고정 상한은 새 시스템에 적용하지 않는다.
- 댓글: V2 일정·작성 회원에 연결하고 본문 길이·공백·승인 상태를 서버에서 검증한다. Kakao 원본 댓글을 새 회원 작성 댓글로 취급하지 않는다.
- 일정 정보 변경은 RSVP를 갱신하지 않는다. 참석 변경·정원 축소·일정 취소가 같은 일정에 대해 일관된 잠금 규칙을 사용해야 한다.
- `version` 등으로 오래된 화면의 일정 수정 충돌을 감지하고 재확인을 안내한다. 중복 생성·전송과 실패 재시도도 검증한다.
- 일정이 취소되면 새 RSVP와 댓글을 허용할지 명시적으로 정한다. 구현 기본값은 새 쓰기 차단 및 기존 댓글 본인/관리자 삭제 허용이다. 상세 설계의 상태별 규칙을 따른다.
- 기존 `events`의 일반 행사 기능은 이번 핵심 범위에서 제외한다. V2 독립 운영에서 이를 노출할 경우 기존 공유 테이블에 쓰는 경로를 남기지 않도록 별도 결정한다.
- 원격 저장 실패를 로컬 저장 성공으로 표시하지 않는다. 시험용 로컬 모드와 실제 회원 운영 모드를 구분한다.

## 4. 권장 권한 모델

| 사용자 | 일정 | RSVP | 댓글 |
| --- | --- | --- | --- |
| 비로그인·pending·disabled·비활성 회원 | 새 V2 일정 열람·쓰기 불가 | 열람·변경 불가 | 열람·작성·변경 불가 |
| 승인된 활성 회원 | 생성, 본인 작성 일정 수정·취소 | 본인 상태만 변경 | 작성·본인 삭제, 수정 제공 여부 미정 |
| 승인된 관리자 | 전체 일정 관리 | 타인 응답 대리 변경은 초기 범위에서 제외 | 운영상 필요한 댓글 관리 |

모든 회원에게 타인의 일정 편집을 허용하지 않는 것을 기본안으로 한다. 관리자 판정은 승인 상태·활성 회원·역할을 사용하고 로그인 Provider나 닉네임을 권한 근거로 삼지 않는다.

김지석 Kakao 계정은 회원 승인 화면 개발에 대한 후속 사용자 승인에 따라 `approved/admin`으로 지정했다. Google 관리자 계정은 그대로 유지했다. 다른 계정에 관리자 권한을 자동 승계하지 않으며, 승인 화면은 일반회원 승인·이용 중지·재개만 제공한다.

RLS·테이블 grants·RPC 검증을 함께 설계한다. 클라이언트가 작성자, 다른 회원 ID, 상태를 위조해도 서버에서 거부해야 한다. 승인/역할 수정은 관리자 경로만 허용한다. 기존 owner 정책을 새 테이블에 무조건 복제하지 않는다.

## 5. 확정 정책과 남은 미정 사항

사용자가 “세 가지 모두 추천대로”라고 답해 다음을 확정했다.

- 새 V2 일정 상세·명단·댓글은 승인된 활성 회원만 열람한다. V1의 기존 공개 범위는 유지한다.
- 일정은 승인된 활성 작성자와 관리자만 수정·취소하며 기록을 보존한다. 일반 운영 UI에 완전 삭제는 제공하지 않는다.
- 기본 정원은 16명이며 일정 편집 권한자가 일정별로 변경할 수 있다.

아래 항목은 추가 구체화가 필요하다. 세 가지 선택을 다른 정책이나 사용자 역할 변경에 대한 승인으로 확대하지 않는다.

| 항목 | 권장 기본안 | 확정이 필요한 시점 |
| --- | --- | --- |
| 모집·시간 기준 마감 | 마감 후 신규 참석 차단, 기존 참석 철회 허용. 시작 이후 RSVP 변경 차단 | 구현 기본값 정리 완료 |
| 취소 후 쓰기 | 새 쓰기 차단, 기존 댓글 본인/관리자 삭제 예외 | 구현 기본값 정리 완료 |
| 댓글 수정 | 기존 작성·본인 삭제부터 유지, 수정은 후속 여부 결정 | 댓글 기능 이식 전 |

## 10. C단계 후속 검증 (2026-09-17)

### 동시성

`python3 scripts/test-v2-concurrency.py`로 일회용 로컬 PostgreSQL 17.11 클러스터를 구성했다. 두 psql 백엔드를 열고 첫 트랜잭션이 잠금을 유지하는 동안 두 번째 세션의 `pg_stat_activity.wait_event_type=Lock`을 확인한 후 첫 트랜잭션을 commit했다. 성공/거부 SQLSTATE와 최종 행 수·정원·버전을 확인했다.

8개 모두 통과: 마지막 한 자리, 정원 축소 선행, 참석 선행 후 정원 축소 거부, 취소 선행 후 참석 거부, 참석 선행 후 취소 및 기록 보존, 같은 ID의 동시 생성, 같은 ID의 동시 댓글, 같은 버전의 동시 편집.

시험은 동일 migration과 최소 공유 스키마 fixture를 사용한다. 원격 운영 DB와 연결하지 않았고, 완료 후 시험 서버를 종료하고 임시 클러스터를 제거했다. 재현용 Homebrew `postgresql@17` 및 의존성은 설치된 상태이며 자동 시작 서비스는 등록하지 않았다. 다른 설치 위치에서는 `PG_BIN`에 PostgreSQL bin 경로를 지정한다. 잠금 기준은 [PostgreSQL 공식 문서](https://www.postgresql.org/docs/current/explicit-locking.html)를 참고했다.


### V1 서비스워커 간섭 — 미해결 운영 조건

실제 배포된 V1 `sw.js`의 캐시 버전 `af3f9d1`을 읽어 제한된 모의 실행 환경에서 재현했다. 파일 SHA-256: `1358b65409d0e90dbfa00684861ee579852745ad57ab58f711855d314045ba62`.

- V1 activate 핸들러가 자신의 캐시 외 모든 origin 캐시를 삭제하므로 V2 캐시도 삭제한다. 일반 방문마다가 아니라 새 워커 활성화 때 발생한다.
- V1 notificationclick 핸들러는 경로 구분 없이 같은 origin 창을 선택하므로 V2 창을 V1으로 이동시킬 수 있다.
- V2 워커는 자체 경로·캐시로 범위를 제한하지만, V1 워커의 위 행동을 막지는 못한다.
- 이 결과는 DB 응답 유실을 뜻하지 않는다. 캐시 유지와 화면 이동의 격리 문제가 남았다는 의미다. 실제 사용자의 설치된 PWA 상태는 별도 확인 대상이다.

재현:

```sh
curl -fsSL https://cafesowoo.github.io/tennis-homepage/sw.js -o tmp/v1-deployed-sw.js
node scripts/check-v1-coexistence.cjs
```

**권고:** V1을 수정하지 않는 조건에서는 V2에 별도 도메인/서브도메인을 연결해 origin을 분리한다. GitHub Pages 호스팅과 저장소는 유지할 수 있다. 운영 주소 선택 후 Pages/DNS/HTTPS, V2 redirect 설정, Supabase 허용 redirect와 실제 Kakao 복귀, PWA scope를 함께 검증한다. Provider 설정 전체를 바꾸거나 기존 V1 redirect를 제거하지 않는다. 도메인 구매·DNS·OAuth 설정 변경·배포는 이번에 실행하지 않았다.

## 13. 관리자 회원 승인 화면

사용자의 명시적 진행 요청에 따라 김지석 Kakao 계정만 관리자로 지정했다. 같은 회원의 기존 Google 관리자 계정과 V1 코드·배포·기존 정책은 그대로 유지했다. 관리자 지정으로 V2 일정·댓글의 기존 관리자 권한도 적용된다.

사용법: 상단 사람/톱니 아이콘 **회원 승인 관리** → 승인 대기 계정 확인 → 실제 회원 본인 확인 → 연결 회원 직접 선택 → 승인. 대상 회원은 새로고침하면 이용할 수 있다. 승인 완료/이용 중지 필터에서 중지·재개 가능하다. 첫 회원이 로그인해야 대기 목록에 나타나며 명단에 없는 신규 회원 생성은 이 화면 범위에 포함하지 않는다.

- `v2-admin.js`의 독립 대화상자로 구현. 모바일·데스크톱 모두 지원하고 관리자 권한 상실·로그아웃·계정 변경 시 목록을 비우고 닫는다.
- 새 migration `20260917121424_v2_member_approval_admin.sql`: 전용 조회·승인 RPC만 추가. 기존 테이블/정책은 수정하지 않았다. 목록과 변경 대상은 Auth의 서버 관리 Provider가 Kakao인 계정으로 제한한다.
- 서버에서 승인된 활성 관리자만 허용. 자기 자신·관리자·Google 계정 변경을 새 RPC에서 차단한다. 역할 변경 인자를 제공하지 않고 기존 회원 연결을 다른 사람으로 재지정하지 않는다.
- 활성 회원만 승인하며, 한 회원의 중복된 승인 Kakao 계정은 차단한다. 기존 Google 계정 연결은 중복 차단 대상이 아니다. 갱신 시각으로 오래된 화면의 덮어쓰기를 차단한다.
- 위 제한은 새 승인 RPC의 계약이다. 기존 관리자의 직접 테이블 접근 정책은 보존했으므로 그 경로까지 새 RPC 제약이 강제된다고 주장하지 않는다.
- Node 자동 테스트 19개 통과. 새 DB 테스트는 일반회원·익명·비활성 관리자 차단, 역할 주입/자기 변경/Google 변경 금지, 활성 회원·중복 연결·재연결·오래된 수정 차단, 승인·중지·재개를 검증했다.
- 실제 원격 DB에서도 가짜 회원/계정을 트랜잭션 안에 만들고 승인·충돌·중지·재개·일반회원 읽기/쓰기 거부를 검증한 뒤 rollback했다. 실제 타 회원의 승인은 수행하지 않았다.
- 모의 SDK 브라우저 시험: 390×844 및 1280×900에서 선택 없이 승인 거부, 직접 선택 후 승인→중지→재개, 권한 회수 후 버튼/목록 숨김 통과.
- Supabase 보안 점검은 기존 유출 비밀번호 보호 경고만 남으며 새 경고 없음. 설정은 바꾸지 않았다.

## 15. 일정 제목 HTML 해석 방지 (2026-09-18)

회원 입력 제목이 일정 상세 h2와 목록 버튼 aria-label에서 escaping 없이 출력되던 두 지점을 수정했다. 목록의 주말 강조 helper는 기존부터 먼저 escapeHTML을 호출하고 있었고, 행사 제목·일정 충돌 안내·수정폼 value·검색 문자열 경로도 확인했다. 원본 제목 저장 방식은 바꾸지 않고 HTML 출력 시점에 인코딩한다.

따옴표·꺾쇠·앰퍼샌드·주말 표기를 포함한 모의 제목으로 실제 렌더링 함수를 실행해 상세/목록 텍스트와 접근성 설명이 그대로 유지되고 추가 HTML 요소나 속성이 생기지 않음을 검증한다. 시험은 localhost 모의 SDK에서만 수행하며 운영 DB에는 시험 문자열을 저장하지 않는다. 기존 생성·수정·RSVP·댓글·취소·로그아웃 흐름도 함께 재검증한다. V1 및 DB 정책은 변경하지 않는다.

## 16. 소수 회원 시험용 의견 보내기 (2026-09-18)

승인된 활성 회원에게 모든 주요 화면의 우측 하단에 **의견 보내기**를 제공한다. 오류·불편·제안과 최대 4,000자 내용을 등록하고, 본인 의견의 접수·확인 중·수정 완료 상태를 확인한다. 관리자는 같은 창에서 전체 의견과 처리 상태 변경을 이용한다. 이번 범위는 피드백 기능이며 별도 시험 일정 구분 기능은 포함하지 않는다.

- `v2-feedback.js` 대화상자와 `v2_feedback` 테이블, 전용 등록/상태 변경 RPC를 추가했다. 기존 일정·회원 승인·V1 테이블과 정책은 변경하지 않았다.
- 승인·활성 여부를 서버에서 검사한다. RLS는 본인 Auth 계정 또는 관리자만 조회하게 하고, 브라우저의 직접 INSERT/UPDATE/DELETE는 허용하지 않는다. 작성자·이름·등록 시각은 서버가 결정하며 회원이 다른 작성자를 지정할 수 없다.
- 일정 상세에서 열면 관련 V2 일정 ID, 그 외에는 현재 화면 이름을 저장한다. GitHub Pages가 `build-info.js`에 배포 커밋을 기록한다. 화면·버전은 문제 재현용 참고값이며 권한 판단에 쓰지 않는다. URL·토큰·브라우저 로그·사진은 수집하지 않는다.
- 같은 요청 ID의 재시도는 기존 의견을 반환한다. 다른 내용으로 요청 ID를 재사용할 수 없다. 관리자 상태 수정은 버전 검사와 행 잠금으로 오래된 화면의 덮어쓰기를 막는다.
- 동적 내용은 textContent로 출력한다. 로그아웃·계정/관리자 역할 변경 때 목록·작성 내용을 비우고 창을 닫으며 늦게 도착한 응답을 무시한다. 등록 후 목록 갱신 실패는 저장 실패와 구분해 안내한다.
- 자동 테스트 23개 통과. 피드백 시험은 본인/타인/관리자/승인 대기/중지/익명 권한, 직접 쓰기 금지, 빈 내용·길이·버전 입력 검증, 중복 요청, 상태 변경 충돌을 확인한다.
- Playwright 모의 SDK 시험은 390×844와 1280×900에서 등록·새로고침·관리자 상태 변경·HTML 문자 안전 출력·권한 해제 시 화면 정리를 확인했다. 가로 넘침과 스크립트 오류 없음.
- 원격 DB에서 트랜잭션으로 동일 요청 재시도·회원 직접 쓰기/상태 변경 거부·관리자 처리·버전 충돌·미승인 계정 조회 차단을 검증 후 rollback했다. 시험 의견과 시험 회원은 남기지 않았다.
- Supabase 보안 점검에 새 경고 없음. 기존 공용 Auth의 [유출 비밀번호 보호 경고](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection)는 기존 상태를 유지했다.

운영 안내: 승인된 회원은 의견 보내기에서 제출하고 같은 창의 내 의견에서 확인한다. 관리자는 전체 의견에서 처리 상태를 저장한다. 승인 전 로그인 장애는 아직 이 기능에 접근할 수 없으므로 카카오톡으로 받는다. 정식 오픈 후에도 이 기능을 계속 사용할 수 있다.

## 17. 연습용 일정 표시 운영 규칙 (2026-09-18)

사용자 선택에 따라 소수 회원 시험에서는 연습용 일정의 제목 앞에 `[테스트]`를 직접 붙인다. 예: `[테스트] 참석·댓글 연습`. 별도 체크박스나 테스트 모드는 추가하지 않는다.

- 실제 모임 일정과 V1에서 가져온 일정은 기존 제목을 유지한다. 정식 오픈 전이라는 이유로 모든 일정을 테스트로 바꾸지 않는다.
- 연습 일정을 생성할 때 제목에 표시하고, 이미 만든 연습 일정은 작성자 또는 관리자가 제목을 수정한다.
- 연습이 끝나면 해당 일정을 취소해 참석·댓글 기록을 보존한다.
- `[테스트]`는 사람이 구분하기 위한 제목 표시다. 참석·댓글 등 동작은 일반 일정과 같으며 자동 제외·자동 삭제 기능은 없다.
- 시험 중 발견한 문제는 의견 보내기로 접수한다. 별도 구분 기능은 실제 운영에서 필요해질 때 검토한다.

## 18. 관리자 일반 회원 화면 미리보기 (2026-09-18)

실제 승인된 관리자에게 왼쪽 아래 `일반 회원으로 보기` 버튼을 제공한다. 전환하면 관리자 메뉴·타인 일정 관리·타인 댓글 삭제·피드백 관리 버튼이 숨겨지고, 피드백은 작성자 Auth ID로 조회 범위를 제한한다. `회원 보기 중 · 관리자 복귀`를 누르면 돌아온다. 전환 시 관리자 목록과 피드백 창을 비워 늦은 응답이 다시 나타나지 않도록 한다.

이는 화면 미리보기이며 Auth 세션·DB 역할·RLS를 바꾸지 않는다. 서버 권한을 검증하는 일반 회원 테스트를 대체하지 않는다. 보기 선택은 현재 페이지 메모리에만 유지하며 새로고침·로그아웃·계정 변경 시 초기화한다. 일반 회원에게는 전환 버튼을 제공하지 않는다.

검증: 자동 테스트 29개 통과. 모의 SDK 브라우저에서 관리자→회원→관리자 전환, 회원 보기의 본인 피드백만 조회, 관리자 컨트롤 숨김/복원, 로그인 ID와 admin 역할 유지, 모바일 가로 넘침 없음 및 스크립트 오류 없음을 확인했다. V1과 DB 변경 없음.
