- 상위 기준: [독립 운영 전환 계획](v2-independent-operation-transition-plan.md)

## 1. 이번에 확인한 운영 경계

### 최초 설정 점검 (후속 실행 검증은 6절 참고)

`/Users/dorm/.codex/automations/automation-4/automation.toml`의 이름은 `🎾 카카오톡 테니스 일정 업데이트`, 상태는 **ACTIVE**였다. 저장된 과거 README의 PAUSED 표기는 현재 설정과 다르다.

- 설정된 프롬프트는 오늘 포함 미래 카카오 일정을 Supabase에 반영한다.
- 대상 목록은 `schedules`, `members`, `courts`, `court_units`이며, `discussions` 조회·수정은 제외한다.
- 날짜·시작/종료 시간·코트·세부 코트로 기존 일정을 찾고, 변경분만 반영하도록 지시한다. 비카카오 일정은 수정·삭제하지 않도록 명시한다.
- 이것은 현재 **설정 확인**이다. 최근 실행 성공, 실제 실행 SQL, 쓰기 역할의 권한 범위까지 확인한 것은 아니다. 자동화를 실행하거나 수정하지 않았다.
- 같은 DB의 새 테이블을 자동으로 대상으로 삼는 설정은 확인되지 않았다. 그러나 자연어 지침은 DB 수준의 접근 제한이 아니므로, 높은 권한의 실행 도구가 새 테이블에 접근할 수 없다고 단정하지 않는다.

병행 운영 검증 시 최근 실행의 실제 변경 대상과 공통 회원·코트 변경 내용을 확인한다. 자동화 중지·프롬프트 수정·권한 축소는 이번 작업에서 하지 않는다.

### Storage·공통 데이터

원격 DB 조회에서 `court-images`, `schedule-photos` 모두 `public=true`, 최대 5 MiB였다. 쓰기 정책은 기존 owner 이메일 기준이다. 기존 bucket과 정책은 그대로 둔다.

공개 bucket의 파일은 URL을 아는 사람이 열 수 있으므로, 새 회원 전용 사진에 기존 `getPublicUrl()` 방식을 쓰지 않는다. 별도 private bucket에서 승인 기반 다운로드를 사용한다. 짧은 유효기간의 signed URL을 사용할 경우 로그아웃이나 권한 회수 후에도 만료까지 URL이 유효할 수 있음을 고려한다. [Supabase Storage 공식 문서](https://supabase.com/docs/guides/storage/buckets/fundamentals)

기존 `members`·일정·댓글의 공개 정책과 정적 데이터는 이번에 비공개로 바꾸지 않는다. 따라서 새 정책이 보장할 수 있는 범위는 **새 V2 데이터**이며, 과거 공개 기록까지 비공개로 전환되는 것은 아니다.

## 2. 사용자 확정 정책과 후속 기본안

사용자는 세 가지 질문에 “세 가지 모두 추천대로”라고 답했다. 아래 정책을 구현 기준으로 확정한다. 이는 코드·DB 적용이나 배포 완료를 의미하지 않는다.

| 항목 | 확정 정책 | 상태 |
| --- | --- | --- |
| 새 일정 상세·명단·댓글 읽기 | 승인된 활성 회원만. 비로그인·pending·disabled·비활성 회원 열람 불가 | 사용자 확정 |
| 일정 편집·취소 | 승인된 활성 작성자와 관리자만, 기록 보존. 일반 운영 UI에 완전 삭제 미제공 | 사용자 확정 |
| 기본 정원 | 16명, 일정 편집 권한자가 일정별 변경 가능 | 사용자 확정 |

공개 정책은 새 V2 데이터에 적용하며 V1과 과거 공개 기록에는 소급 적용하지 않는다. 사용자 역할은 변경하지 않고 김지석 Kakao 계정은 일반회원으로 유지한다.

다음은 후속 진행 요청에 따라 정리한 **구현 기본 규칙**이다. 사용자가 별도로 선택한 정책으로 표현하지 않으며, 세부 동작은 이후 변경할 수 있다. 이번에는 문서에만 반영한다.

- 모집 마감: 새 참석 전환은 막되, 기존 참석자의 불참·미정 변경은 허용해 빠지는 사실을 반영한다. 정원이 찼을 때도 같은 원칙을 사용한다.
- 시작 시각 이후: 모든 RSVP 변경과 일반 일정 편집을 막고 댓글은 취소되지 않은 일정에서 계속 허용한다. 관리자도 일반 편집으로 과거 일정을 미래로 옮겨 마감을 우회할 수 없다. 운영상 정정 기능은 후속 범위다. 시간은 Asia/Seoul로 표시하고 DB는 절대 시각으로 저장하며 서버 현재 시각으로 판정한다.
- 취소: 작성자/관리자는 시작 이후에도 취소할 수 있다. 일정·참석·댓글 기록은 유지하고 새 RSVP·댓글 작성과 일정·사진 변경은 차단한다. 기존 댓글의 본인/관리자 삭제는 취소 후에도 허용한다. 취소가 댓글을 자동 삭제하지 않는다.
- 마감 해제는 시작 전 작성자/관리자가 할 수 있다. 만석은 응답 수로 계산하며, 한 명이 빠져도 수동 마감은 자동 해제하지 않는다. 정원은 양의 정수이며 현재 참석 수보다 작게 줄일 수 없다.
- 신규 일정·시간 변경은 미래 시작 시각과 시작보다 늦은 종료 시각을 요구한다. 상태 검사는 취소 여부, 시작 시각, 모집 마감/정원 순서로 한다.
- 취소 복구·일정 완전 삭제·댓글 수정·대리 RSVP·자동 재초대·자동 알림은 초기 범위에서 제외한다.
- 일정의 시간/장소 변경은 기존 참석을 자동 재확정 또는 초기화하지 않는다. 변경 사실을 표시하고 참석 유지 안내를 제공한다. 재응답 요청 기능은 별도 결정한다.
- 작성자 자신의 참석도 명시적으로 선택한다. 일정 생성만으로 타인이나 작성자를 자동 참석시키지 않는다.

## 3. 테이블 계약 초안

### `v2_schedules`

- `id`: UUID. 생성 요청의 동일 ID 재시도는 동일 작성자·동일 입력일 때 기존 결과를 반환하고 다른 입력은 충돌 처리.
- `creator_member_id`, `created_by_user_id`: 서버가 승인 계정에서 결정. 일반 수정 입력에서 제외.
- `host_member_id`: 진행자 표시용, 편집 권한과 분리. 초기에는 본인 또는 미지정만 제공하고 타인 지정은 후속 범위로 둔다.
- `title`, `starts_at`, `ends_at`, `court_id`, `court_unit_id`, `capacity`, `registration_closed`.
- `status`: active/cancelled. `cancelled_at`, `cancelled_by_user_id`로 취소 사실 보존.
- `created_at`, `updated_at`, `updated_by_user_id`, `version`.
- `court_name_snapshot`, `court_unit_label_snapshot`, `creator_name_snapshot`: 공통 정보 변경·삭제 후에도 당시 표시를 유지하기 위한 최소값. 개인정보 보관 범위는 별도 정책에 따른다.
- 사진 지원 시 `photo_path`와 표시 위치. 영구 public URL이나 signed URL 자체는 저장하지 않는다.
- 이전 작업 시에만 `legacy_schedule_id`의 유일성으로 중복 이전을 방지한다. 실시간 동기화 식별자로 사용하지 않는다.

공통 `members`·`courts`·`court_units`에 새 RESTRICT FK를 추가하면 기존 V1 삭제가 갑자기 실패할 수 있다. CASCADE는 V1 삭제가 V2 기록을 지우는 문제가 있다. 따라서 **초기에는 공통 테이블에 대한 논리 참조와 RPC의 존재/활성 검사, 표시 snapshot을 권장**한다. 공유 대상을 삭제해도 V2 기록은 유지되며, 새 생성·수정에서는 유효한 대상을 요구한다. 공통 ID 재사용 금지와 고아 참조 점검을 검증 항목에 넣는다. 완전한 참조 무결성보다 V1 동작 보존을 우선한 의도적인 선택이며, 추후 기준정보 분리가 필요해지면 재검토한다.

### `v2_schedule_rsvps`

- PK `(schedule_id, member_id)`, 상태 attending/declined/pending, `updated_at`, `updated_by_user_id`.
- `schedule_id`는 새 V2 일정에 FK로 연결한다. 기존 일정 ID 입력은 거부한다.
- 응답 없음은 행 없음으로 표현, 명시적으로 미정을 선택하면 pending 행을 저장한다.
- 기존 Kakao source 배열·override·declines를 읽거나 쓰지 않는다. 참석 수는 이 테이블에서 계산한다.
- 이전 응답을 수용할 때만 provenance 필드가 필요하며, 사용자 본인이 응답한 시점과 구분한다.

### `v2_discussions`

- `id`, V2 `schedule_id` FK, `member_id`, `created_by_user_id`, `message`, `created_at`.
- 본문은 앞뒤 공백 제거 후 1~2,000자. 작성자·시각은 서버가 결정한다.
- 동일 UUID 재시도는 중복 댓글을 만들지 않는다. 일반 수정은 우선 제공하지 않는다.
- 본인 또는 관리자의 삭제만 허용한다. 계정 간 본인 판정은 승인된 `member_id`로 통일한다.

## 4. RPC·RLS와 동시성 계약

새 exposed 테이블은 RLS를 활성화하고 새 테이블의 grants를 명시한다. 기존 테이블의 grants·정책은 변경하지 않는다. authenticated의 새 테이블 직접 INSERT/UPDATE/DELETE는 열지 않고 검증된 RPC를 쓰기 진입점으로 삼는 안이다. SELECT는 승인된 활성 회원으로 제한한다. [Supabase RLS 공식 문서](https://supabase.com/docs/guides/database/postgres/row-level-security)

| RPC 제안 | 검사와 변경 범위 |
| --- | --- |
| `v2_create_schedule` | 승인·활성 확인, 작성자 서버 결정, 시간/정원/코트 일치 검증, V2 일정만 생성 |
| `v2_update_schedule` | 일정 잠금, 작성자/관리자, expected_version, 허용 필드만 수정. 현재 참석 수보다 작은 정원 거부 |
| `v2_cancel_schedule` | 동일 잠금·권한·버전 검사, 취소 메타데이터만 변경. 반복 취소는 일관된 결과 반환 |
| `v2_set_my_rsvp` | 승인 계정에서 member ID 결정, 일정 잠금, 취소/마감/정원/시간 검사, 본인 행만 upsert |
| `v2_add_discussion` | 승인·활성·일정 상태·길이 검사. 취소와 경쟁할 때 일정 잠금 후 insert |
| `v2_delete_discussion` | 승인·활성 및 본인/관리자 검사. 존재하지 않는 행·권한 없음 처리 통일 |

여러 행을 변경하는 경로는 먼저 일정 행을 잠그고 나서 자식 행을 처리한다. 마지막 자리 참석 경쟁, 정원 축소와 참석 경쟁, 취소와 새 댓글/참석 경쟁에서 동일 순서를 사용한다. 일정 metadata version은 편집·취소에 사용하고 RSVP마다 올려 불필요한 편집 충돌을 만들지 않는다.

RPC에서 필요한 권한 상승은 기존 패턴처럼 비공개 schema의 좁은 함수에 한정하고, public wrapper는 invoker로 둔다. 비공개 함수도 로그인/승인/활성/소유권을 자체 검사한다. search_path 고정, PUBLIC/anon execute 회수, authenticated에 필요한 execute만 부여한다. RPC 입력의 회원 ID·작성자 필드를 신뢰하지 않는다.

## 5. 화면과 파일별 구현 예정 범위

- `index.html`: 기존 표현·폼 재사용, V2 조회/RPC 어댑터 추가, 일반회원 일정 작성 UI, 작성자/관리자 편집 버튼, 취소 표시. 기존 테이블 쓰기 호출을 V2 운영에서 실행하지 않도록 제거/격리.
- `club/app.js`, `club/index.html`: 공개 보조 화면이 새 명단·댓글의 우회 노출 경로가 되지 않도록 승인 흐름 연결 또는 소개 화면만 제공.
- `sw.js`: private 데이터·사진·인증 URL을 공용 캐시에 넣지 않음. 현재 외부 Supabase 요청은 same-origin 조건으로 캐시 대상이 아니며 이 경계를 유지.
- `.github/workflows/pages.yml`: 회원 전용 데이터의 정적 snapshot 배포 금지. 승인 전 데이터 선조회/fallback과 함께 점검. 기존 공개 파일은 새 비공개 데이터의 대체 원본으로 사용하지 않음.
- 신규 migration/test: 새 테이블·RPC·RLS와 실패/경쟁 검증 추가. 기존 마이그레이션을 수정·재실행하지 않음.
- 사진 제공 시 별도 private bucket. 객체 경로를 `schedule_uuid/random_uuid.ext`로 제한하고 부모 일정·작성자/관리자 검사. 업로드→DB 연결 실패의 고아 파일과 이전 사진 교체 실패를 복구하도록 설계. Storage와 DB가 하나의 트랜잭션이 아님을 고려.

로그아웃·승인 철회 시 메모리의 일정·댓글·이미지 URL과 화면을 비운다. 네트워크 오류를 ‘일정 없음’으로 처리하거나 공개 seed 데이터를 보여주지 않는다. 권한 변경 전 이미 내려받은 내용까지 회수할 수 있다고 보장하지 않는다.
